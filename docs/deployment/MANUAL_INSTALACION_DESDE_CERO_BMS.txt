======================================================================
0. OBJETIVO Y ALCANCE
======================================================================

Este manual responde al siguiente escenario:

  "Tengo un Ubuntu Server recién instalado y necesito instalar el BMS."

Está escrito para que la instalación pueda realizarla una persona distinta
al desarrollador original, con conocimientos básicos de Linux y redes.

Este documento cubre desde el primer inicio de sesión en Ubuntu Server hasta
que el BMS queda operativo, validado y preparado para reiniciar solo.

NO explica el desarrollo interno de Node-RED ni la lógica de los PLC.
Para entender la arquitectura, backup, cifrado, seguridad, MQTT retained y
criterios de diseño consultar también:

  MANUAL_MAESTRO_DEPLOYMENT_BMS.txt
  MANUAL_BACKUP_CIFRADO_BMS.txt
  MANUAL_RESTAURACION_MIGRACION_BMS.txt
  ANEXO_DIAGNOSTICO_DEPLOYMENT_BMS.txt

La instalación completa se basa en dos fuentes:

  1. Git
     Código y configuración reproducible del BMS.

  2. Backup cifrado
     Estado persistente del sistema: FUXA, runtime de Node-RED y Mosquitto.

Para recuperar un BMS existente se necesitan AMBAS cosas.

======================================================================
3. SUPUESTOS DEL HOST
======================================================================

Este procedimiento fue validado en Ubuntu Server x86_64 y el mismo Core fue
probado en aarch64.

La instalación de Docker soporta ambas arquitecturas, pero cada host debe
obtener o construir imágenes Docker para SU propia arquitectura.

La configuración validada utiliza un usuario de operación con:

  UID 1000
  GID 1000

Antes de continuar ejecutar:

  id
  id -u
  id -g

Resultado de referencia:

  uid=1000(...)
  gid=1000(...)

Si el usuario que ejecutará el BMS NO es UID/GID 1000:1000, NO continuar a
ciegas. Node-RED utiliza bind mounts y su imagen trabaja normalmente con UID
1000. Consultar el Manual de Deployment y validar permisos antes de poner el
sistema en producción.

En este manual se usa como ejemplo el usuario:

  juancasas

Ruta validada:

  /home/juancasas/bms-sanatorio

Si se utiliza otro usuario, reemplazar la ruta por:

  /home/USUARIO/bms-sanatorio

siempre que UID/GID y permisos hayan sido validados.

======================================================================
7. INSTALAR DOCKER ENGINE Y DOCKER COMPOSE
======================================================================

Se utiliza Docker Engine del repositorio oficial de Docker.

7.1 Eliminar paquetes que puedan entrar en conflicto

En una instalación nueva normalmente no habrá ninguno.

Ejecutar:

  for pkg in docker.io docker-doc docker-compose docker-compose-v2 \
             podman-docker containerd runc; do
      sudo apt-get remove -y "$pkg" 2>/dev/null || true
  done

7.2 Crear keyring e instalar la clave oficial

  sudo apt update
  sudo apt install -y ca-certificates curl

  sudo install -m 0755 -d /etc/apt/keyrings

  sudo curl -fsSL \
    https://download.docker.com/linux/ubuntu/gpg \
    -o /etc/apt/keyrings/docker.asc

  sudo chmod a+r /etc/apt/keyrings/docker.asc

7.3 Agregar repositorio Docker

Copiar y ejecutar el siguiente bloque completo:

  . /etc/os-release

  printf '%s\n' \
    'Types: deb' \
    'URIs: https://download.docker.com/linux/ubuntu' \
    "Suites: ${UBUNTU_CODENAME:-$VERSION_CODENAME}" \
    'Components: stable' \
    "Architectures: $(dpkg --print-architecture)" \
    'Signed-By: /etc/apt/keyrings/docker.asc' \
    | sudo tee /etc/apt/sources.list.d/docker.sources >/dev/null

Comprobar el archivo creado:

  cat /etc/apt/sources.list.d/docker.sources

Debe contener seis campos: Types, URIs, Suites, Components, Architectures y
Signed-By.

7.4 Instalar Docker

  sudo apt update

  sudo apt install -y \
    docker-ce \
    docker-ce-cli \
    containerd.io \
    docker-buildx-plugin \
    docker-compose-plugin

7.5 Habilitar Docker

  sudo systemctl enable --now docker

Comprobar:

  sudo systemctl status docker --no-pager

Debe aparecer:

  active (running)

7.6 Prueba de Docker

  sudo docker run --rm hello-world

La ejecución debe terminar correctamente.

ADVERTENCIA DE FIREWALL:

Docker gestiona reglas de red propias. Los puertos publicados por Docker no
deben asumirse protegidos sólo porque UFW esté activo. En este BMS la defensa
principal es que 1880, 1881 y 1883 se publican únicamente sobre 127.0.0.1 y
se verifica al final con ss. Si TICS requiere reglas adicionales, deben
implementarse de acuerdo con la política Docker/iptables de la institución.

9. PREPARAR ACCESO AL REPOSITORIO GIT
======================================================================

Comprobar si ya existe una clave SSH:

  ls -la ~/.ssh

Si TICS ya entregó una clave autorizada, instalarla según el procedimiento
institucional.

Si se debe generar una nueva clave y la política lo permite:

  ssh-keygen -t ed25519 -C "bms-sanatorio"

La clave pública se obtiene con:

  cat ~/.ssh/id_ed25519.pub

Esa clave pública debe ser autorizada en el repositorio GitHub.

NO enviar ni copiar la clave privada id_ed25519 a terceros.

Comprobar acceso al repositorio sin clonarlo:

  git ls-remote \
    git@github.com:Juancasas95/bms-sanatorio.git \
    HEAD

Si pide confirmar la identidad del servidor GitHub, seguir el procedimiento
de seguridad de TICS para verificar la huella del host antes de aceptar.

Si el comando devuelve un hash, el acceso está funcionando.

Si devuelve:

  Permission denied (publickey)

NO continuar. Solicitar acceso al repositorio.

12. PREPARAR DIRECTORIOS PERSISTENTES Y PERMISOS
======================================================================

Evitar que Docker cree directorios importantes como root por accidente.

Ejecutar:

  cd "$HOME/bms-sanatorio"

  mkdir -p \
    backups \
    fuxa/appdata \
    fuxa/db \
    fuxa/images \
    fuxa/logs \
    mosquitto/data \
    mosquitto/log

Dar permisos al directorio de backups:

  chmod 775 backups

Comprobar:

  stat -c '%A | %a | %U:%G | UID=%u GID=%g | %n' backups

El usuario debe poder escribir:

  if touch backups/.install-write-test; then
      echo "BACKUPS ESCRIBIBLE - OK"
      rm -f backups/.install-write-test
  else
      echo "ERROR - backups/ no es escribible"
      exit 1
  fi

NO aplicar chmod 777 a mosquitto/data ni a sus bases.

El restore normalizará los permisos de Mosquitto correctamente.

14. INSTALAR DEPENDENCIAS DE NODE-RED
======================================================================

En un clone nuevo, nodered/node_modules puede no existir.

Desde la raíz del proyecto:

  cd "$HOME/bms-sanatorio"

Ejecutar:

  docker run --rm \
    -v "$PWD/nodered:/data" \
    nodered/node-red:5.0.1 \
    sh -c 'cd /data && npm ci --omit=dev --no-audit --no-fund'

Esto utiliza package-lock.json para instalar versiones reproducibles.

Durante la migración de Fase 7 se verificaron nodos requeridos de Modbus,
email y WhatsApp.

No aprobar scripts nativos desconocidos a ciegas si npm muestra una
advertencia nueva. Consultar el Manual de Deployment / diagnóstico.

Comprobar:

  test -d nodered/node_modules \
    && echo "NODE-RED DEPENDENCIAS OK"


======================================================================
15. NO ARRANCAR TODAVIA TODO EL BMS
======================================================================

En una recuperación desde backup NO ejecutar todavía:

  docker compose up -d

Primero se debe restaurar el estado persistente.

La razón principal es seguridad MQTT:

  una base Mosquitto restaurada puede contener retained antiguos.

El procedimiento seguro arranca Mosquitto primero, limpia comandos y recién
entonces inicia Node-RED.

======================================================================

  mkdir -p "$HOME/bms-install-input"
  chmod 700 "$HOME/bms-install-input"

  ARCHIVO.tar.gz.age

======================================================================

20. EJECUTAR RESTORE --CHECK
======================================================================

  cd "$HOME/bms-sanatorio"

  ./scripts/restore.sh \
    "$HOME/bms-install-input/bms-backup-restored.tar.gz" \

Debe finalizar con:

  El backup pasó todas las validaciones.
  NO se modificó ningún archivo.

Revisar especialmente:

  Hostname origen
  Git branch
  Git commit
  Git destino

Si aparece un AVISO por commits diferentes:

  no es automáticamente un error,
  pero debe entenderse antes de continuar.

Para una recuperación exacta, preferir el commit registrado en el manifest.

23. ARRANQUE SEGURO - PASO 2 - LIMPIAR COMANDOS MQTT RETAINED
======================================================================

Ejecutar:

  docker run --rm \
    --network docker_default \
    -e MQTT_HOST=bms-mosquitto \
    -e MQTT_PORT=1883 \
    -v "$PWD/scripts/mqtt-cleanup.sh:/scripts/mqtt-cleanup.sh:ro" \
    --entrypoint /bin/sh \
    eclipse-mosquitto:2.0 \
    /scripts/mqtt-cleanup.sh

Resultado esperado:

  Mosquitto disponible.
  Limpiando retained de comandos /write...
  Limpiando retained de diagnóstico...
  MQTT COMMAND CLEANUP OK

Este paso borra comandos históricos peligrosos, pero no la telemetría retained
normal.


======================================================================
24. ARRANQUE SEGURO - PASO 3 - COMPROBAR QUE NO QUEDEN RETAINED PELIGROSOS
======================================================================

Ejecutar:

  timeout 5 \
  docker exec bms-mosquitto \
    mosquitto_sub \
    -h localhost \
    -p 1883 \
    -t 'bms/#' \
    -v \
    > /tmp/bms-install-retained.txt || true

  DANGEROUS="$(
    awk '{print $1}' /tmp/bms-install-retained.txt \
      | grep -E '(/write$|^bms/diagnostico/comando$)' \
      | sort -u
  )"

  if [ -z "$DANGEROUS" ]; then
      echo "OK - NO HAY RETAINED PELIGROSOS"
  else
      echo "ERROR - RETAINED PELIGROSOS:"
      echo "$DANGEROUS"
  fi

No continuar si aparece ERROR.

  nc -vz 10.3.5.107 502
  nc -vz 10.0.21.200 502
  nc -vz 172.16.252.244 502

Si alguno falla:

  revisar IP del servidor
  revisar rutas
  revisar VLAN
  revisar firewall
  consultar TICS

No cambiar las IP de equipos en el BMS sólo porque una prueba de red falla.

======================================================================
32. REINICIO COMPLETO DEL SERVIDOR
======================================================================

Una instalación no se considera terminada hasta superar un reboot.

Antes:

  cd "$HOME/bms-sanatorio"

  git rev-parse --short HEAD
  git status --short
  docker ps
  timedatectl

Reiniciar:

  sudo reboot

Esperar a que el host vuelva.

Entrar nuevamente por SSH.

Comprobar:

  uptime
  timedatectl

  docker ps \
    --format "table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}"

Esperar a que Node-RED muestre healthy.

Comprobar logs:

  docker logs --since 5m bms-nodered 2>&1 \
    | grep -E 'Connected to broker|BMS READY|RETAINED|No existe devices|SCHENIDER|FC Not Valid'

Esperado:

  Connected to broker
  ========== BMS READY ==========

Comprobar FUXA desde navegador otra vez.

NOTA IMPORTANTE:

El cleanup manual es obligatorio después de un RESTORE antes del primer
arranque de Node-RED.

En un reboot normal, los Safety Guards de Node-RED protegen contra replay de
comandos retained históricos. El reboot final fue validado en Fase 7.

33. ELIMINAR MATERIAL SENSIBLE TEMPORAL
======================================================================

Después de confirmar que el BMS funciona:

Eliminar el TAR descifrado:

  rm -f "$HOME/bms-install-input/bms-backup-restored.tar.gz"

Eliminar la clave privada del servidor:

  rm -f "$HOME/bms-install-input/bms-recovery.key"

Comprobar que no quedó otra copia:

  find "$HOME" \
    -type f \
    -name 'bms-recovery.key' \
    -print

Resultado esperado:

  ninguna salida

El backup .age y su .sha256 pueden conservarse según la política de backup,
porque están cifrados.

  MANUAL_BACKUP_CIFRADO_BMS.txt

Este backup nuevo demuestra que el servidor instalado también puede cumplir
su ciclo normal de operación y recuperación.

  logs del contenedor afectado
